# src/lib rules

- Prototype mode (REAL_AUTH_ENABLED=false in featureFlags.ts): SignIn checks no credentials and sets the chosen roleStore preset; MedicationSourceGate always serves medicationDemoStore (permissions follow the demo view), eMAR client pages read loadDemoClientEmar, corrections append and never overwrite; real-auth/Cloud medication code stays intact for when real accounts return — avoids a second login while keeping the backend path.

- Controlled medication support uses medicationRules for task-specific outcomes and medicationStore/medication-workspace for authenticated, scoped, append-only Cloud records; visit checkout never completes medication, AI never selects outcomes, and exceptions require separate human acknowledgement/follow-up — preserves clinical intent and an auditable trail.

- Eligible-only best fit is derived by carerBestFit.ts using visible ordered factors; suggestions only open manual assignment — avoids opaque scores, cached fit and roster writes.

- Event-to-care-plan review rules live only in src/lib/carePlanReviewRules.ts; src/lib/carePlanReviewTrigger.ts wires incidentsStore.submit to associatedIncidentsStore and carePlansStore ReviewSuggestions — one suggestion system, and a suggestion never edits plan text.
- carePlanTemplateModel defines versioned templates and standard categories; carePlansStore applies updates only through draft "Use latest template" — renaming cannot break rules or change published plans.
- Ask LogUp proposals come only from proposeCarePlanChanges (src/lib/carePlanAssistant.ts) as a ChangeSet; carePlansStore.acceptAssistantChange is the only path into a draft and records the original proposal — so a real model can replace the rules without touching the UI, and nothing enters a plan unaccepted. Section order lives on the version (sectionOrderOverride) and changes only via drafts; templates are never touched.
- Assessments are records in src/lib/assessmentsStore.ts (results of the provider's own tool, never scored by LogUp); "Consider reassessment" is decided only by reassessmentsForEvent in carePlanReviewRules.ts and each line stores its trigger(s) — so every suggestion can say why it exists.
- Insights Events/Care Planning cards are calculated live in src/lib/insightSignals.ts from the source stores (never seeded); dismissals and missing-link resolutions are append-only there, and names in a narrative never link a service user automatically — so every card can be traced to the records it counts.
- Residents are admitted through the Admit flow; Directory of Residents fields, required flags and the admission care plan deadline live only in src/lib/residentDirectory.ts, and document pre-fill comes only from extractAdmissionDetails (src/lib/admissionAssistant.ts) as AI drafts that must be confirmed — so regulatory wording changes in one place and a real model can replace the simulation.
- Policy Help (policyHelp.ts) answers only from each policy's current published version via approvedPolicySources, re-derived on policiesStore changes; AI citations must match supplied source IDs or the answer is 'not found'; signed-out users get verbatim excerpts; audit keeps question/source/found only.
- Demo (no session) visit notes: CareVoiceRecorder offers DEMO_VOICE_TRANSCRIPT instead of recording, and demoMissingQuestions (demoVisitNote.ts) asks rule-based questions for unmentioned topics; answers are appended to Follow-up, and the carer confirms before saving. Keeps the AI note flow demonstrable without inventing care.
- Manager Home "What needs my attention today?" is derived only in operationalOverview.ts from live stores (visits, notes, eMAR demo exceptions, Events, Tasks); Insights stays separate for trends — no seeded counts on Home.
- Medication follow-ups are ordinary tasksStore tasks with medicationLinks (client, visit, dose task, outcome, exception IDs); completing one never changes the exception or dose record — exception acknowledgement/resolution stays a separate human step.
- Care Assurance insights are derived only in careAssurance.ts (rule vs ai_simulated keyword themes over confirmed notes); actions create insightLinks tasks, never edit records. Chronology (serviceUserTimeline) and the evidence pack read the same live stores; historical demo notes come from demoHistoricalNotes.ts — so every card, entry and pack line traces to a record.
- Live visit reviews append separate acknowledgement, findings and evidence-based assessments in visitAlertReviewStore; explicit follow-up saves use shared Tasks with visit/client/alert/review IDs and same-action duplicate checks. Task cards/history derive live without changing attendance — keeps source evidence separate from manager conclusions.
